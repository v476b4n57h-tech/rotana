## 0. الصورة العامة: كيف تعمل التقنيات معاً؟

| الأداة         | دورها في المشروع                                                                |
| -------------- | ------------------------------------------------------------------------------- |
| **Next.js**    | يبني صفحات الموقع ولوحة الإدارة، ويشغّل كوداً على الخادم بأمان (مثل تأكيد الحجز)  |
| **TypeScript** | جافاسكربت مع "أنواع"، فيكتشف كثيراً من الأخطاء قبل تشغيل الموقع                  |
| **Supabase**   | قاعدة البيانات (PostgreSQL)، وتسجيل الدخول، وتخزين الصور، والمهام المجدولة      |
| **GitHub**     | يحفظ كل نسخ الكود. لكل مرحلة تعديلات واضحة يمكن مراجعتها والتراجع عنها          |
| **Vercel**     | ينشر الموقع على الإنترنت، ويعطيك رابط معاينة لكل تعديل قبل أن يصل للموقع الرسمي |

```
الزبون (المتصفح)
   ↓
Vercel ── يشغّل Next.js (الصفحات + كود الخادم)
   ↓
Supabase ── قاعدة البيانات + الحسابات + الصور
            (قاعدة البيانات نفسها ترفض أي وصول غير مسموح، عبر RLS)
```

**المبدأ الأهم في الخطة:** قاعدة البيانات هي خط الدفاع الأخير. حتى لو وُجد خطأ في كود الموقع، تبقى قاعدة البيانات نفسها رافضةً لحجزين في نفس الوقت، ورافضةً أن يرى صالونٌ بيانات صالون آخر.

## 1. حماية النسخة الأصلية وطريقة العمل على GitHub

- فرع `main` **لن يُلمس إطلاقاً**. ملف `index.html` الحالي يبقى فيه كما هو.
- كل العمل يجري في فرع منفصل. الفرع المقترح هو `claude/intelligent-fermat-o1jgwp`، وهو فرع جديد لا علاقة له بـ `main`.
- داخل الفرع الجديد يُنسخ الملف الأصلي إلى `legacy/index.html` كمرجع للمقارنة البصرية فقط.
- يُقترح وضع "علامة" (tag) على النسخة الحالية باسم `v0-static-demo`، للعودة إليها بضغطة زر في أي وقت. لن تُنشأ إلا بموافقة صاحب المشروع.
- كل مرحلة تنتهي بـ commit واضح، ويعطي Vercel رابط معاينة (Preview) للتجربة قبل أي شيء آخر.
- دمج العمل في `main` ونشره على الموقع الرسمي **لا يحدث إلا بموافقة صريحة** عند الإطلاق.

> **ما هو الفرع (branch)؟** نسخة موازية من المشروع تعمل عليها بحرية. الأصل لا يتأثر حتى تقرر أنت دمجهما.

## 2. المحافظة على التصميم 100%

هذا أكثر جزء يحرص عليه صاحب المشروع، لذلك له خطة خاصة:

1. **الألوان:** تُنقل متغيرات الألوان الموجودة في `:root` كما هي حرفياً إلى `globals.css`، بما فيها ألوان الوضع الليلي.
2. **الخطوط:** نفس الخطين بنفس الأوزان (Cormorant Garamond 500/600 و Jost 400/500)، لكن عبر `next/font`. هكذا تُحمَّل من الموقع مباشرة، فيصبح التحميل أسرع ولا يحدث وميض عند ظهور الخط.
3. **CSS عادي بنفس أسماء الكلاسات** (`.btn` و `.svc` و `.choice` و `.slot`…)، وبدون Tailwind. السبب أن إعادة الكتابة بأداة أخرى تسبب فروقات صغيرة في الشكل.
4. **الحركات** تبقى كما هي: الشريط المتحرك، والكلمة المتبدلة "hem / haar"، والسلايدر، والظهور التدريجي عند التمرير، ونافذة عرض الصور.
5. **الأيقونات:** نفس أيقونات Font Awesome، لكن من حزمة npm بدل CDN.
6. **الصور:** تُستخرج الصور الـ 22 المدمجة داخل الملف إلى ملفات مستقلة، وتُعرض عبر `next/image`، فيتحول حجم الصفحة من 2 ميغابايت إلى جزء صغير منه. ولاحقاً تُرفع الصور الحقيقية من لوحة الإدارة.
7. **اختبار بصري آلي (Playwright):** يأخذ لقطات شاشة للنسخة القديمة والجديدة، على الحاسوب والجوال وفي الوضعين الفاتح والليلي، ويقارنهما. أي اختلاف ظاهر يفشل معه الاختبار.

**الإضافة الوحيدة الضرورية في تجربة المستخدم:** خطوة أخيرة في الحجز لإدخال الاسم والهاتف والبريد، لأن الحجز الحقيقي يحتاجها. ستُصمَّم بنفس الأسلوب والألوان تماماً. لوحة الإدارة أيضاً ستستخدم نفس الهوية.

## 4. قاعدة البيانات

### المبدأ: كل جدول يحمل `salon_id`

أي معلومة (خدمة، حلاق، حجز، زبون) مرتبطة بصالون محدد. هذا أساس عزل الصالونات من اليوم الأول، حتى لو بدأنا بصالون واحد.

| الجدول           | ماذا يحفظ                                                                                                                 |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `salons`         | الصالون: الاسم، المعرّف في الرابط (`rotana`)، المنطقة الزمنية (Europe/Amsterdam)، العنوان، الهاتف، KVK، BTW، روابط التواصل |
| `salon_domains`  | النطاقات المرتبطة بكل صالون (rotana.nl…)                                                                                  |
| `salon_members`  | من يدير الصالون ودوره: `owner` (المالك) أو `admin` (مدير) أو `staff` (حلاق)                                               |
| `staff`          | الحلاقون: الاسم، الصورة، التخصص، القسم (رجال/نساء)، نشط أم لا                                                             |
| `services`       | الخدمات: الاسم، الوصف، القسم، **السعر بالسنت**، **المدة بالدقائق**، وقت راحة بعد الخدمة                                   |
| `staff_services` | أي حلاق يقدم أي خدمة                                                                                                      |
| `working_hours`  | ساعات عمل كل حلاق لكل يوم من أيام الأسبوع                                                                                 |
| `time_off`       | إجازات وعطل (لحلاق معين أو للصالون كله)                                                                                   |
| `customers`      | زبائن الصالون: الاسم، الهاتف، البريد، وربط اختياري بحساب مسجّل                                                             |
| `appointments`   | الحجوزات (التفاصيل أدناه)                                                                                                 |
| `audit_log`      | سجل من غيّر ماذا ومتى، للمراجعة والأمان                                                                                    |
| `notifications`  | الرسائل المرسلة (تأكيد، تذكير) وحالتها                                                                                    |

**جدول الحجوزات `appointments`:**
`salon_id`، `staff_id`، `service_id`، `customer_id`، `starts_at`، `ends_at`، `status` (pending / confirmed / cancelled / completed / no_show)، **سعر ومدة محفوظان لحظة الحجز**، ملاحظات، رمز إدارة مشفّر، وتاريخ الإنشاء.

> **لماذا نحفظ السعر لحظة الحجز؟** لو رُفع السعر غداً، تبقى الحجوزات القديمة بسعرها الأصلي.
>
> **لماذا السعر بالسنت (2500 بدل 25.00)؟** الأعداد الصحيحة لا تسبب أخطاء تقريب في الحسابات المالية.
>
> **الوقت** يُحفظ بصيغة `timestamptz` (وقت عالمي)، ويُعرض بتوقيت أمستردام. هذا يمنع مشاكل التوقيت الصيفي والشتوي.

### حارس العزل الثاني: مفاتيح مركّبة

لا يكفي أن يحمل الحجز `salon_id`. يجب أن تضمن قاعدة البيانات أن الحلاق المذكور في الحجز **من نفس الصالون**:

```sql
-- الحجز يشير إلى (الصالون + الحلاق) معاً، فيستحيل ربط حجز في صالون A بحلاق من صالون B
foreign key (salon_id, staff_id) references staff (salon_id, id)
```

## 5. منع تعارض الحجوزات

المشكلة: زبونان يضغطان "تأكيد" على نفس الموعد في نفس الثانية. الحل على ثلاث طبقات:

**الطبقة 1: قيد داخل قاعدة البيانات (الأهم).**

```sql
create extension if not exists btree_gist;

alter table appointments add constraint no_double_booking
  exclude using gist (
    staff_id with =,                                  -- نفس الحلاق
    tstzrange(starts_at, ends_at, '[)') with &&       -- وفترتان متداخلتان
  ) where (status in ('pending', 'confirmed'));       -- الحجوزات الملغاة لا تُحسب
```

> **بالعربي البسيط:** قاعدة البيانات نفسها ترفض حفظ حجز لنفس الحلاق إذا تداخل وقته مع حجز آخر نشط. هذا يعمل حتى لو وصل طلبان في نفس اللحظة بالضبط، والكود لا يستطيع تجاوزه.

**الطبقة 2: دالة حجز واحدة على الخادم (`book_appointment`).** الحجز لا يُكتب في الجدول مباشرة أبداً، بل عبر دالة تتحقق من:

- أن الحلاق يقدّم هذه الخدمة.
- أن الوقت ضمن ساعات عمله وليس في إجازة.
- أن الموعد ليس في الماضي، وأنه يحترم الحد الأدنى للحجز المسبق (مثلاً قبل ساعتين على الأقل).
- حساب وقت الانتهاء **من مدة الخدمة في قاعدة البيانات**، لا مما يرسله المتصفح، لأن المتصفح يمكن التلاعب به.

إذا رفض القيد الحجز، يرى الزبون رسالة لطيفة: "هذا الموعد حُجز للتو، اختر وقتاً آخر".

**الطبقة 3: أوقات متاحة حقيقية.** تُستبدل المعادلة الوهمية الحالية بدالة `get_available_slots`. تحسب الأوقات الفارغة فعلياً: ساعات العمل، ناقص الحجوزات، ناقص الإجازات، مع مراعاة مدة الخدمة ووقت الراحة بعدها.

**حماية من الإساءة:**

- اختبار Cloudflare Turnstile، وهو بديل CAPTCHA غير مزعج، لمنع الحجوزات الآلية.
- حد لعدد المحاولات لكل جهاز.
- مفتاح "عدم التكرار" حتى لا يسجّل الضغط المزدوج على الزر حجزين.

## 6. الصلاحيات وأمان البيانات (RLS)

> **ما هو RLS (Row Level Security)؟** قواعد مكتوبة داخل قاعدة البيانات تحدد لكل مستخدم أي "صفوف" يحق له رؤيتها أو تعديلها. حتى لو أخطأ كود الموقع، تبقى قاعدة البيانات رافضةً.

| الدور                     | ماذا يرى ويفعل                                                                                    |
| ------------------------- | ------------------------------------------------------------------------------------------------- |
| **زائر**                  | يرى الخدمات والأسعار والفريق النشط وساعات العمل والأوقات المتاحة **فقط**، ولا يرى أي بيانات زبائن |
| **زبون مسجّل**             | يرى حجوزاته هو فقط، ويلغيها أو يعدّلها ضمن المهلة المسموحة                                         |
| **حلاق (staff)**          | يرى مواعيد صالونه، ويحدّث حالة مواعيده (حضر / لم يحضر)                                             |
| **مدير (admin)**          | يدير الحجوزات والخدمات والفريق والإجازات في صالونه فقط                                            |
| **مالك (owner)**          | كل ما سبق، إضافة إلى إعدادات الصالون وإدارة الأعضاء                                               |
| **مالك المنصة** (مستقبلاً) | إدارة الصالونات والاشتراكات، عبر مسار منفصل وتسجيل في السجل                                       |

مثال على قاعدة:

```sql
-- لا يرى الحجوزات إلا أعضاء نفس الصالون
create policy "members read their salon appointments"
on appointments for select
using ( is_salon_member(salon_id) );
```

**قواعد أمان ثابتة في كل المشروع:**

1. RLS مفعّل على **كل** جدول بلا استثناء، مع اختبارات آلية تحاول اختراق العزل (مثلاً: مستخدم من صالون A يحاول قراءة بيانات B، ويجب أن يفشل).
2. مفتاح `service_role` (المفتاح الشامل) لا يوجد إلا على الخادم في متغيرات Vercel السرية، ولا يصل للمتصفح أبداً.
3. التحقق من كل مدخلات المستخدم بمكتبة `zod` قبل أي معالجة.
4. حماية مسار `/admin` بثلاث طبقات: middleware، ثم تحقق في كل صفحة على الخادم، ثم RLS.
5. ترويسات أمان (CSP وغيرها) على كل الصفحات.
6. **GDPR (AVG في هولندا):**
   - البيانات مخزنة في أوروبا: Supabase في فرانكفورت، و Vercel في منطقة `fra1`.
   - موافقة صريحة عند الحجز.
   - إمكانية تصدير بيانات الزبون أو حذفها.
   - حذف أو إخفاء البيانات القديمة بعد مدة محددة.
7. نسخ احتياطي يومي لقاعدة البيانات، يقدمه Supabase في الخطط المدفوعة.

## 7. نظام الحجز من منظور الزبون

نفس الخطوات الحالية تماماً، ثم إضافة في النهاية:

```
رجال / نساء → اختيار الحلاق → الخدمة → اليوم → الوقت (حقيقي الآن)
   → بياناتك (الاسم، الهاتف، البريد + موافقة الخصوصية)   ← جديد
   → تأكيد → شاشة نجاح + بريد تأكيد فيه رابط لإلغاء/تعديل الموعد
```

- **تسجيل الدخول:** بدون كلمة مرور. يصل الزبون رمز أو رابط إلى بريده، وهي طريقة أسهل للزبون وأكثر أماناً. الحساب اختياري.
- **الإلغاء:** من صفحة "حسابي"، أو من الرابط الآمن في البريد دون الحاجة لحساب، ضمن مهلة يحددها الصالون (مثلاً حتى 24 ساعة قبل الموعد).
- **الإشعارات:**
  - بريد تأكيد فوري عبر خدمة Resend.
  - تذكير قبل 24 ساعة بمهمة مجدولة في Supabase.
  - واتساب أو SMS لاحقاً.
- **اختيار "أي حلاق متاح":** إضافة اختيارية تعرض أقرب وقت فارغ عند أي حلاق.

## 9. الجاهزية للتحول إلى SaaS (لعدة صالونات)

ما يُبنى **من البداية** حتى لا نعيد العمل لاحقاً:

- `salon_id` في كل جدول، و RLS مبني على عضوية الصالون.
- توجيه النطاقات عبر `salon_domains` و `middleware.ts`.
- مستخدم واحد يمكن أن يكون زبوناً في عدة صالونات، أو موظفاً في أكثر من صالون.

ما يُضاف **لاحقاً** عند التحول إلى SaaS:

- **هوية بصرية لكل صالون:** جدول `salon_themes` يحفظ قيم متغيرات الألوان والخطوط والشعار. هوية ROTANA الحالية تصبح "الثيم الأول".
- **التسجيل الذاتي:** صالون جديد يسجّل وينشئ موقعه بنفسه.
- **الاشتراكات والفوترة:** Stripe أو Mollie، مع جدول `subscriptions` وحدود لكل باقة (عدد الحلاقين مثلاً).
- **نطاقات خاصة:** ربطها تلقائياً عبر Vercel Domains API.
- **لوحة مالك المنصة** (`/platform`).

## 14. التعديلات المعتمدة (الإصدار 1.1)

اعتمد صاحب المشروع الخطة مع التعديلات التالية. هذا القسم يحدد كيف ينعكس كل تعديل على التصميم الهندسي.

### 14.1 عدة صالونات وعدة فروع لكل صالون (منذ البداية)

التسلسل: **صالون (العلامة التجارية) ← فروع (المواقع الفعلية)**.

| الجدول            | الغرض                                                                      |
| ----------------- | -------------------------------------------------------------------------- |
| `salons`          | الصالون كعلامة: الاسم، الهوية، الإعدادات العامة، KVK و BTW                 |
| `branches`        | الفرع: العنوان، الهاتف، المنطقة الزمنية، ساعات العمل الافتراضية، نشط أم لا |
| `staff_branches`  | أي حلاق يعمل في أي فرع (الحلاق يمكن أن يعمل في أكثر من فرع)                |
| `branch_services` | سعر أو توفر خاص لخدمة في فرع معين (اختياري؛ وإلا يُستخدم سعر الصالون)       |

- `salon_id` يبقى في **كل** جدول، فهو أساس العزل بين الصالونات.
- `branch_id` يُضاف لكل ما يتعلق بمكان: الحجوزات، ساعات العمل، الإجازات، المدفوعات، المصاريف، إقفال الصندوق اليومي.
- المفاتيح المركّبة تضمن أن الفرع والحلاق والخدمة في الحجز كلها من **نفس الصالون**.
- منع التعارض يبقى على مستوى الحلاق (`staff_id`)، فلا يمكن حجز نفس الحلاق في فرعين بنفس الوقت.
- **تجربة المستخدم:** خطوة "اختر الفرع" لا تظهر إلا إذا كان للصالون أكثر من فرع. بفرع واحد، تبقى تجربة ROTANA مطابقة للأصل.
- الصلاحيات يمكن أن تكون على مستوى الصالون كله أو فرع محدد (مثلاً مدير فرع يرى فرعه فقط).

### 14.2 النظام المالي

| الجدول                            | الغرض                                                                                     |
| --------------------------------- | ----------------------------------------------------------------------------------------- |
| `payment_methods`                 | طرق الدفع قابلة للإعداد: نقداً، بطاقة (PIN)، تحويل، بطاقة هدية…                            |
| `vat_rates`                       | نسب BTW مع تاريخ بداية السريان، فلا تُكتب النسب داخل الكود                                 |
| `sales` و `sale_items`            | عملية البيع: خدمات ومنتجات، السعر، الخصم، BTW لكل سطر                                     |
| `payments`                        | الدفعات المرتبطة بكل عملية بيع (يمكن الدفع بأكثر من طريقة)                                |
| `receipts`                        | إيصالات بأرقام متسلسلة لكل فرع                                                            |
| `expenses` و `expense_categories` | المصاريف حسب الفئة والفرع، مع إرفاق صورة الفاتورة                                         |
| `commission_rules`                | نسبة الحلاق: حسب الحلاق، أو الخدمة، أو الفئة، مع تاريخ بداية ونهاية، فيُحفظ تاريخ كل تغيير |
| `commission_entries`              | العمولة المحسوبة لكل بيع، محفوظة لحظة البيع                                               |
| `cash_closings`                   | إقفال الصندوق اليومي لكل فرع                                                              |

**قواعد مالية ثابتة:**

- كل المبالغ بالسنت (أعداد صحيحة). النسب بنقاط الأساس (21% = 2100).
- **السجلات المالية لا تُحذف ولا تُعدّل بعد إقفالها.** التصحيح يكون بقيد عكسي، وكل تغيير يُسجّل في `audit_log`.
- **التقارير:** الإيرادات اليومية والشهرية، لكل فرع ولكل حلاق، والمصاريف، وصافي الربح، والعمولات، وملخص BTW لكل ربع سنة (يساعد في الإقرار الضريبي، لكنه لا يغني عن المحاسب).
- **مدة الحفظ:** القانون الهولندي يُلزم بحفظ السجلات المالية 7 سنوات. عند طلب زبون حذف بياناته (GDPR)، تُخفى هويته في السجلات المالية (anonymization) بدل حذفها.
- **الصلاحيات:** المالك يرى كل الأرقام المالية. المدير حسب ما يسمح به المالك. الحلاق يرى عمولته فقط.
- **ملاحظة:** نسبة BTW على خدمات الحلاقة تُحدَّد مع المحاسب وتُدخل من لوحة الإدارة.

### 14.3 الولاء و VIP والكوبونات (مستقبلاً)

لا تُبنى الآن، لكن البنية تُجهَّز حتى لا نحتاج إعادة بناء لاحقاً:

- مسار حساب السعر في الكود يكون على مراحل منذ البداية: **السعر الأساسي ← الخصومات ← BTW ← الإجمالي**، فيمكن إضافة أي نوع خصم لاحقاً.
- `sale_items` و `appointments` فيها حقول خصم من البداية (`discount_cents` ومصدر الخصم).
- الجداول المستقبلية: `loyalty_programs`، و`loyalty_accounts`، و`loyalty_transactions` (سجل نقاط لا يُحذف)، و`customer_tiers` (VIP)، و`coupons`، و`coupon_redemptions`.
- تُفعَّل بمفاتيح الوظائف (`loyaltyCards` و `vipTiers` و `coupons`)، وهي موجودة الآن في `src/config/features.ts` وكلها مطفأة.

### 14.4 الحجز دون حساب، مع حساب اختياري

- الحجز يتطلب الاسم والهاتف والبريد فقط.
- `customers.user_id` اختياري. عندما ينشئ الزبون حساباً ويؤكد بريده، تُربط حجوزاته السابقة بنفس البريد بحسابه تلقائياً.
- إدارة الموعد بدون حساب عبر رابط آمن في البريد (رمز مشفّر وله مدة صلاحية).
- الحماية: Turnstile، وحد للمحاولات، ومنع الضغط المزدوج.

### 14.5 حساب مستقل لكل حلاق

- كل حلاق له تسجيل دخول خاص، مرتبط بسجله في `staff` عبر `staff.user_id`.
- يرى **مواعيده هو فقط**، وبيانات الزبون الضرورية للموعد (الاسم، والهاتف، والملاحظات)، دون قائمة الزبائن الكاملة أو التقارير المالية للصالون.
- يرى عمولته وساعات عمله، ويمكنه طلب إجازة (يوافق عليها المدير).
- تُفرض هذه الحدود بقواعد RLS، مع اختبارات آلية تتأكد منها.

### 14.6 تأجيل الدفع الإلكتروني

- لا دفع إلكتروني في الإصدار الأول. المفتاح `onlinePayments` مطفأ.
- النظام المالي يسجّل الدفعات في الصالون (نقداً أو بطاقة) يدوياً من لوحة الإدارة.
- جدول `payments` مصمم بحيث يُضاف إليه لاحقاً Mollie أو Stripe دون تغيير البنية.

### 14.7 اللغة الهولندية أولاً

- كل نصوص الموقع في ملفات ترجمة (`src/i18n/messages/nl.json`)، لا مكتوبة داخل المكونات.
- إضافة لغة لاحقاً = إضافة ملف ترجمة جديد.
- نصوص الصالون القابلة للتعديل (مثل "لماذا نحن") تُحفظ في قاعدة البيانات مع عمود للغة (`locale`).

### 14.8 GDPR وفصل الموافقات التسويقية

- جدول `consents`: الزبون، والغرض (`booking` / `marketing_email` / `marketing_sms`)، موافق أم لا، والتاريخ، والمصدر، ونسخة نص الموافقة.
- **الموافقة التسويقية منفصلة تماماً عن الحجز:** مربع اختيار غير محدد مسبقاً، والحجز يعمل بدونه.
- رابط إلغاء الاشتراك في كل رسالة تسويقية.
- حق الاطلاع والتصدير والحذف (مع إخفاء الهوية في السجلات المالية، انظر 14.2).
- البيانات مخزنة في الاتحاد الأوروبي (Frankfurt). سياسة الخصوصية بنسخ مؤرخة.
- سياسة مدة الاحتفاظ: حذف أو إخفاء بيانات الزبائن غير النشطين بعد مدة يحددها المالك.

### 14.9 بنية مرنة قابلة للتوسعة

- **تقسيم حسب الوظائف (modules):** `src/features/booking` و`src/features/finance` و`src/features/staff`… كل وحدة مستقلة قدر الإمكان، فيمكن تعديلها أو إزالتها دون التأثير على غيرها.
- **مفاتيح الوظائف (feature flags):** الآن في `src/config/features.ts`، ولاحقاً لكل صالون في جدول `salon_features`.
- **Migrations:** كل تغيير في قاعدة البيانات ملف مرقّم في `supabase/migrations`، فيمكن التطوير تدريجياً دون فقدان البيانات.
- **الاختبارات الآلية** تحمي ما بُني سابقاً عند إضافة الجديد.
- **لا محتوى مكتوب داخل الكود:** كل ما يتغير يُدار من قاعدة البيانات.

### 14.10 تعديل المحتوى من لوحة الإدارة

يُدار من اللوحة دون تعديل الكود: الخدمات، والأسعار، والمدة، والصور (Supabase Storage)، والموظفون وصورهم، وساعات العمل، والإجازات، والفروع، والعنوان والتواصل، وروابط التواصل الاجتماعي، ونصوص الموقع (`site_content` لكل لغة)، وطرق الدفع، ونسب BTW، ونسب الحلاقين.

### 14.11 المحافظة على التصميم

يبقى ما في القسم 2 كما هو. ومن المرحلة 0:

- متغيرات الألوان والقواعد الأساسية منسوخة حرفياً إلى `src/app/globals.css`، مع اختبار آلي يتأكد من تطابقها مع الأصل.
- نفس الخطوط ونفس الأوزان، مع اختبار آلي.

### 14.12 عدم استخدام بيانات زبائن حقيقية أثناء التطوير

- بيانات التطوير **وهمية فقط** (أسماء ومواعيد مختلقة) في `supabase/seed.sql`.

- سكربت البيانات الوهمية يرفض العمل إذا كان متصلاً بقاعدة الإنتاج.
- البريد في بيئة التطوير لا يُرسل لعناوين حقيقية (يُحوّل لصندوق اختبار).

### 14.14 تحديث هيكل الملفات

يُضاف إلى الهيكل في القسم 3:

```
src/
├─ features/                ← وحدة مستقلة لكل وظيفة
│  ├─ booking/
│  ├─ finance/
│  ├─ staff/
│  ├─ customers/
│  ├─ branches/
│  └─ loyalty/              ← مستقبلاً
├─ config/features.ts       ← مفاتيح الوظائف
├─ i18n/                    ← ملفات اللغات
└─ lib/finance/             ← حسابات المال و BTW والنسب (مع اختبارات)
```

وفي لوحة الإدارة يُضاف: `admin/finance/` (الإيرادات، والمصاريف، والعمولات، والتقارير، و BTW)، و`admin/branches/`، و`admin/content/` (نصوص الموقع والصور)، و`admin/privacy/` (الموافقات وطلبات البيانات).
